# infra/cognito-idc/
Provisioning for the **Amazon Cognito + IAM Identity Center** track. Step numbers and file names are the same as in the interactive pages in [`data/cognito-idc/`](../../data/cognito-idc/) (index: [`data/cognito-idc/README.md`](../../data/cognito-idc/README.md)).
- `01`–`08`: shared foundation and OBO (VPC, Cognito, IdC trusted token issuer, Redshift, runtime). `09`–`12`: 2LO / 3LO. `13`–`14`: web GUIs. `15-rbac-*`: Gateway tool RBAC (demo). `16-mall-*`: Gateway tool RBAC (customer version, Amazon Quick). `17-harden-cognito-email.py`: run once on an existing deployment (see below). `99-teardown.sh`: removes what 01–16 created (see below).
- `lambda/`: `reporting`, `rbac_tools`, `pretoken` (the mall tools Lambda is in `../common/lambda/mall_tools`).
- `policies/`: IAM trust and permission documents. `registry/`: Agent Registry record bodies. `sql/`: Redshift seed and grants. `ops/`: one-off operator helpers (`cognito-disable-self-signup.py` is a dry run by default; it only changes pools named `rsidc-*` in `$RT_REGION`, and only with `--apply`).
Conventions: scripts source `../common/00-config.sh` and use `$ROOT` for repo-relative paths; run them through `infra/common/run.sh`. `14-deploy-webchat.sh` packages the GUIs of both tracks (`webchat/cognito-idc/`, `webchat/entra-id/`). See [`../README.md`](../README.md) for the install order.

## `email` is not user-changeable
The IdC trusted token issuer (`03`), the Pre Token trigger's IdC source (`15-rbac-pretoken.py`) and the 3LO identity check all identify the user by `email`. So:
- No app client can write `email`: `02`, `09`, `13` and `16` set `WriteAttributes` to `name`, `given_name`, `family_name` only (`ReadAttributes` keeps `email`, `email_verified`).
- The pool sets `AttributesRequireVerificationBeforeUpdate=email` with email auto-verification: an email change only takes effect after the new address is verified.
- The Pre Token trigger skips the IdC lookup unless `email_verified` is `true` (fail closed: no IdC roles).
- Users are still created by an administrator only (`AllowAdminCreateUserOnly=true`, no self sign-up).

`17-harden-cognito-email.py` applies the pool and client settings to a deployment created before this change. On a new install, run it once after `10` too (`10-credential-providers.py` rewrites the 3LO client without its attribute lists). Command: `infra/common/run.sh .venv/bin/python infra/cognito-idc/17-harden-cognito-email.py`. `UpdateUserPool` and `UpdateUserPoolClient` reset any setting you omit, so the script does a read-modify-write: it reads the full current pool and client configuration, changes only these fields, writes everything back and prints a before/after diff. It keeps `AllowAdminCreateUserOnly=true` and stops if that is no longer set. It is idempotent and creates no resources.

## Hardening notes (threat model T-02, T-11, T-24, T-32)
- **Gateway role trust (T-32)**: `11`, `15-rbac-gateway.sh` and `16-mall-gateway.sh` trust `bedrock-agentcore.amazonaws.com` only with `aws:SourceAccount` and `aws:SourceArn` = `gateway/<project>-<name>-*` (a name-prefix wildcard, since the role exists before the gateway). Re-running the script re-applies the trust to an existing role (`update-assume-role-policy`).
- **Policy mode (T-02)**: `15-rbac-policy.sh` and `16-mall-policy.sh` (and `entra-id/02-entra-gateway.sh`) default to `ENFORCE`. `LOG_ONLY` must be passed explicitly; it allows every tool for every authenticated caller and only logs decisions, and the script prints a warning.
- **Throttling (T-11)**: `14-deploy-webchat.sh` sets `$default` stage throttling on each GUI's HTTP API (`THROTTLE_RATE=10` req/s, `THROTTLE_BURST=20`, overridable via env). AWS WAF cannot be attached to an API Gateway HTTP API. For production put the GUIs behind CloudFront with an AWS WAF web ACL (rate-based rule, IP set, managed rule groups) and restrict the API to CloudFront (for example an origin-verify header checked in the Lambda).
- **Redshift TLS (T-24)**: `04-redshift-cluster.sh` creates the parameter group `<project>-redshift-pg` with `require_ssl=true` and associates it with the cluster (for an existing cluster it modifies the cluster and reboots it once, a short outage). The cluster stays publicly addressable with `/32` security-group rules; a production deployment should use a private cluster (`publicly-accessible=false`, reached through the VPC). Clients already use TLS: the OBO agent calls `redshift_connector.connect(..., ssl=True)` and the Lambdas and `05-seed-redshift.py` use the Redshift Data API (HTTPS).

## Teardown
`99-teardown.sh [--dry-run] [--yes]` deletes steps 01–16 in dependency order: Pre Token trigger detached from the pool, web GUIs (Lambdas, HTTP APIs, `rsidc-webchat-role`), mall gateway stack (log delivery, targets, gateway, Cedar policies, policy engine, `rsidc-mall-tools`, Quick client, Cognito groups, roles), RBAC stack (same, plus the test workload identity, `rsidc-tool-*`, `rsidc-pretoken-roles` with its `live` alias, project-owned IdC groups), 2LO/3LO (runtimes, gateway, `rsidc-reporting`, credential providers, roles, Cognito domain), S3 artifacts, Redshift (no final snapshot) and its IdC applications, the Cognito pool, then the runtime VPC. The IdC instance, its users and pre-existing groups are never touched.
Run `common/99-teardown.sh` and `entra-id/99-teardown.sh` first: the Entra gateway reuses the mall Lambda and role, and the script refuses to run while `ENTRA_GW_ID` is in `state.env` (override with `ALLOW_WITH_ENTRA=1`). Type `yes` at the prompt or pass `--yes`.
